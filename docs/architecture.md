# Application architecture

## Server-first data flow

1. Species profiles and their ecological/model configuration are validated from version-controlled files at build time.
2. The offline GIS worker builds authoritative 250 × 250 m static cells from ICGC elevation and land cover plus ISRIC SoilGrids.
3. Supabase stores those cells and a normalized Open-Meteo grid. Many model cells share one weather point at the provider's real resolution.
4. Scheduled Edge Functions refresh regional and provider-grid weather, recording provenance, confidence, unavailable fields, cursors, and audited runs. The 9 km soil-grid refresh also stores a separate homogeneous five-day ECMWF/Open-Meteo forecast issuance. A daily database job then materializes current conditions for the 2.5, 5, and 10 km display levels.
5. A separate monthly pipeline reads whitelisted fungal occurrences from GBIF, quality-filters them, and maps them immediately to 10 km support cells. Exact source coordinates are never persisted.
6. Next.js server code reads bounded environmental inputs and applies the same versioned scoring model used by species pages. Historical occurrence support is joined only as independent corroborating context.
7. The browser renders a user-selectable basemap (ICGC standard, muted, or hybrid orthophoto; or standard OpenStreetMap raster tiles) and requests a zoom- and viewport-appropriate overlay: 250 m locally, then 1 km, 2.5 km, 5 km, or 10 km summaries as the view widens. A visible-cell budget automatically selects a coarser supported grid for unusually wide viewports, preventing truncated thousand-cell reads while preserving close-zoom detail. Basemap attribution remains visible and the preference is stored locally in the browser.

## Architectural decisions

- Species ecology and model weights stay in version control as the scoring single source of truth; Supabase stores observations and normalized snapshots, not competing model configuration.
- The 250 m grid is the canonical static model unit. Larger map cells are prebuilt summaries of verified 250 m evidence, never mushroom occurrences or guarantees of presence. Versioned per-species compatible-cover fractions are precomputed into compact arrays for every existing 1, 2.5, 5, and 10 km display cell; zero-coverage cells remain explicit array zeros rather than absent evidence. Coarse current-condition summaries are refreshed after daily weather ingestion and both caches are read directly during zoom interactions.
- Source resolution is preserved independently from display resolution. A coarse display cell therefore remains explicit about the atmospheric, soil-moisture, terrain, and land-cover resolutions behind it.
- Zoom aggregation averages representative conditions but retains safety-sensitive temporal extremes: the coldest minimum, hottest maximum, strongest wind and highest frost-hour count inside each display cell.
- Weather windows are explicit: “now” is Open-Meteo’s latest model estimate; short summaries cover the trailing 24 hours; temperature and frost history covers 10 days; precipitation and reference evapotranspiration (ET₀) cover 3, 7 and 30 days; and shallow soil moisture retains a 7-day minimum, mean, maximum and trend. Dry-spell length uses 1 mm in a rolling 24-hour block as the reset threshold. All windows use the Europe/Madrid time zone and contain model values, not station observations.
- Future trends are projected environmental suitability, never a promise of mushroom emergence. Each daily target from +1 through +5 days recomputes the same 24-hour, 3/7/10/30-day and soil-memory windows from observed-plus-forecast hourly values, then runs the existing versioned species scorer with the selected cell's static habitat evidence. Forecast atmosphere uses one consistent ECMWF IFS HRES 9 km issuance because the current AROME model ends after roughly two days; shallow soil moisture keeps the model's existing Open-Meteo 3–9 cm layer at 9 km. Forecast rows are stored separately from observations, carry their issue and valid times, and are withheld after 36 hours, as soon as any target has expired, or whenever required hourly inputs are incomplete. Atmosphere and soil-forecast provider health and ingestion cursors are independent, so one degraded stream cannot block the other or current soil refreshes. The interface keeps the AROME observation and ECMWF projection lines visually detached and reports projected change from +1 to +5 days, avoiding a misleading cross-model delta. It uses an explicit dashed series, per-horizon confidence, and a warning that suitability is not fruiting occurrence.
- Static GIS processing runs outside Edge Functions because authoritative raster products are too large for request-bound runtimes.
- ICGC 1:50,000 geological units are kept in compact side tables as display-only context, separate from soil properties and scoring snapshots. Exact cells retain mapped/class/unit coverage sampled across the 250 m area; larger display cells are area-weighted from those canonical children, and map scale is never reported as metre resolution.
- Read functions return only verified cells in bounded views. Exact sensitive ecological locations are not collected or exposed.
- Historical occurrences are presence-only evidence, not training labels or a score multiplier. A record can corroborate ecological plausibility, but missing records never reduce suitability or imply absence. FungaCAT is accessed through its GBIF dataset key so the same records cannot be ingested twice under two source names.
- Occurrence responses expose counts, year ranges, provenance, DOI, and licence only at a minimum 10 km grid. The raw GBIF coordinates exist only in the authenticated ingestion request and the database mapping function; neither the source coordinates nor public point features are stored.
- Species-page habitat maps encode static land-cover/altitude/pH compatibility only. The GIS worker preserves every recognized land-cover fraction sampled within each 250 m cell, so a 35% compatible cover contributes 0.35 rather than turning the whole cell on. Blue intensity uses that linear compatible-cover percentage adjusted by the shared altitude edge taper; the unweighted cover percentage remains separate for the prediction habitat factor so altitude is not counted twice. A separate purple hatch marks compatible cells whose centres fall inside a 10 km occurrence-support cell, so historical corroboration cannot be mistaken for stronger habitat. Occurrence counts do not alter habitat compatibility; records outside compatible habitat remain a documented disagreement and unsampled cells are never excluded.
- Habitat reads use a compact generated forest field plus generated numeric altitude/pH fields on the canonical 250 m cells. `static_values` remains the verified source of truth. A measured covering index is retained because it keeps country-wide habitat aggregation index-only; live profiling showed that removing it caused a cold read to scan most of the table heap. The database reader plans exact 250 m viewport reads separately from coarse coverage aggregation, and coarse viewports use numeric bounds on the already-filtered resolution rather than materializing wide PostGIS rows.
- Predictions expose factor contributions and a composite `modelVersion` covering both versioned species ecology and the scoring algorithm. Temperature suitability uses the trailing 10-day mean, with the same window's minimum, maximum, and frost hours retaining acute cold and heat interruptions; current and 24-hour values remain contextual fallbacks. Air-humidity suitability remains responsive to the trailing 24-hour mean; a drier 7-day mean below 65% contributes a limited 25% persistence penalty, while an older humid week never raises or masks the current 24-hour score. Rainfall suitability is continuous: rain from 3 and 7 days is reduced by a conservative share of ET₀, while rain versus ET₀ on days 8–30, dry-spell length, 7-day soil-moisture floor/mean/trend, and the species' configured dependence on prior moisture determine antecedent readiness and short-lived carryover. A 7-day-only legacy snapshot is incomplete and cannot publish a prediction. Predictions consume the same exact 250 m forest/altitude/pH coverage aggregated for the species habitat map. That percentage is the habitat factor instead of a coarse label-match band; zero compatible coverage and inactive months are hard zeroes. For a coarse cell, the altitude factor is the compatible-cover-weighted taper `Σ(C × A) / ΣC`, not a suitability score calculated from its arithmetic mean elevation. Every prediction cell blends its score-band colour with the zero-score colour by the raw compatible-cover fraction, so sparse compatible habitat cannot paint the whole cell as fully suitable at any zoom. Soil moisture also uses a continuous piecewise-linear response around the preference in the versioned species profile, without coarse score bands. Predictions are otherwise withheld or capped when evidence is incomplete, stale, severely hot/dry, recently frozen, or only in a possible month. Concurrent rainfall, temperature, soil-moisture, and humidity stress lowers the publication ceiling proportionally to severity rather than snapping it to fixed 35/55 plateaus. A recent frost cap applies even when the 10-day mean is otherwise favorable, with limited tolerance only where the species profile explicitly documents it.
- A profile can opt into `predictionMode: "habitat_only"` when the short-term above-ground fruiting model is scientifically inapplicable. The scorer and prediction API then withhold a score, the public map offers compatibility only, and the profile must carry an explicit caveat. `Tuber melanosporum` uses this mode because its subterranean ascocarps develop over months and depend on host colonization, soil structure, management, and conditions at depth that the current inputs do not observe.
- A species page never scores a region centroid. Its regional indicator is the habitat-coverage-weighted median of publishable 10 km prediction cells assigned to the selected region, restricted to cells with non-zero exact 250 m compatible coverage. The interface also exposes the weighted interquartile range and cell count so the single number cannot be mistaken for uniform conditions across the region.
- The version-controlled habitat altitude range is the ecological core. Altitude remains at 100 through the interior, tapers linearly from 100 to 75 during the 100 m inside either documented limit, and then falls linearly to zero across the 100 m uncertainty margin outside each limit. For ranges narrower than 200 m, the two inner tapers meet at the midpoint. The potential-habitat reader receives the core limits, applies the shared taper and outer envelope to each exact 250 m cell, and aggregates both raw compatible coverage and altitude-weighted map intensity; cells at or beyond the zero-score edge remain excluded.
- Viewport coordinates are expanded to resolution-aware cache buckets before requests are made. Static habitat responses receive a one-day shared-cache lifetime and a model-version cache key; regional environmental snapshots and current prediction inputs keep a five-minute server/shared-cache lifetime. Browser map requests have a bounded deadline and discard obsolete responses after pans or species changes, so a stalled provider cannot leave the overlay loading indefinitely. Interactive 1/2.5/5/10 km reads use the compact species cache, while only close 250 m views evaluate canonical evidence on demand. Browser-facing map responses omit repeated provenance that is not used for drawing and negotiate gzip for material JSON bodies. Species profiles defer MapLibre and the static habitat request until the map is near the viewport, with a height-preserving accessible placeholder. A profile is not readable until every geographic cache batch is marked complete, so an interrupted rebuild cannot turn missing work into false zeroes. An optional versioned object-storage origin can serve static habitat JSON, with automatic database fallback. This keeps object storage off the critical path unless it is explicitly configured and populated.
- The hosted database is operated to a sub-450 MB target after physical compaction. The redundant 500 m materialization is omitted; the 1 km layer remains active until the original close-zoom transition to exact indexed 250 m cells. Only three forecast issue dates are retained in PostgreSQL; longer hindcast validation should use an external export after measuring storage. Self-hosted Supabase/PostgreSQL in Docker is the capacity fallback if compaction plus retention cannot keep the database comfortably below the 500 MB Free limit.

Operational details, rebuild commands, and pipeline schedules are documented in [`supabase/README.md`](../supabase/README.md).
