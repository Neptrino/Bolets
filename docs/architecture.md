# Application architecture

## Server-first data flow

1. Species profiles and their ecological/model configuration are validated from version-controlled files at build time.
2. The offline GIS worker builds authoritative 250 × 250 m static cells from ICGC elevation and land cover plus ISRIC SoilGrids.
3. Supabase stores those cells and a normalized Open-Meteo grid. Many model cells share one weather point at the provider's real resolution.
4. Scheduled Edge Functions refresh regional and provider-grid weather, recording provenance, confidence, unavailable fields, cursors, and audited runs. The 9 km soil-grid refresh also stores a separate homogeneous five-day ECMWF/Open-Meteo forecast issuance. An idempotent completion gate materializes current conditions for the 2.5, 5, and 10 km display levels as soon as the observed atmosphere and soil streams finish; forecast degradation never blocks those current caches.
5. A separate monthly pipeline reads whitelisted fungal occurrences from GBIF, quality-filters them, and maps them immediately to 10 km support cells. Exact source coordinates are never persisted.
6. Next.js server code reads bounded environmental inputs and applies the versioned hydrothermal scorer using the same species ecology shown on profile pages. Historical occurrence support is joined only as independent corroborating context.
7. The browser renders a user-selectable basemap (ICGC standard, muted, or hybrid orthophoto; or standard OpenStreetMap raster tiles) and requests a zoom- and viewport-appropriate overlay: 250 m locally, then 1 km, 2.5 km, 5 km, or 10 km summaries as the view widens. A visible-cell budget automatically selects a coarser supported grid for unusually wide viewports, preventing truncated thousand-cell reads while preserving close-zoom detail. Basemap attribution remains visible and the preference is stored locally in the browser.

## Architectural decisions

- Species ecology, guild priors, species overrides, response curves, temporal windows, and hydrothermal exponents stay in version control as the scoring single source of truth; Supabase stores normalized environmental snapshots, not competing model configuration. Each supported species' numeric temperature envelope initializes the midpoint optimum and cold/warm half-response widths; an explicit species-literature override can replace those values.
- The 250 m grid is the canonical static model unit. Larger map cells are prebuilt summaries of verified 250 m evidence, never mushroom occurrences or guarantees of presence. Versioned per-species compatible-cover fractions are precomputed into compact arrays for every existing 1, 2.5, 5, and 10 km display cell; zero-coverage cells remain explicit array zeros rather than absent evidence. Coarse current-condition summaries are refreshed after daily weather ingestion and both caches are read directly during zoom interactions.
- Source resolution is preserved independently from display resolution. A coarse display cell therefore remains explicit about the atmospheric, soil-moisture, terrain, and land-cover resolutions behind it.
- Zoom aggregation averages representative conditions but retains safety-sensitive temporal extremes: the coldest minimum, hottest maximum, strongest wind and highest frost-hour count inside each display cell.
- Cell timelines use the same visible 250 m, 1 km, 2.5 km, 5 km, or 10 km unit selected on the map. Coarse observed and forecast points aggregate the provider locations linked to that display cell with the same representative-value and safety-extreme rules as its current prediction; the interface never requires selecting an arbitrary 250 m child.
- Weather windows are explicit and versioned. “Now” is Open-Meteo's latest model estimate; `hydrothermal-v1` consumes a configured 14- or 20-day temperature mean with frost and ≥27 °C heat-hour counts over the same window, effective rain and wet-day frequency over 14 or 21 days (26 for `Boletus edulis`), 7-day mean temperature and humidity for derived vapour-pressure deficit, dry-spell length, and the 7-day mean and minimum of shallow relative extractable water. A wet day starts at 1 mm; accumulated effective rain is `max(0, rain - wetDays × 1 mm - 0.5 × ET0)`. All windows use the Europe/Madrid time zone and contain model values, not station observations.
- Future trends project the same ordinal environmental indices, never mushroom emergence or presence probability. Every forecast issuance stores a horizon-zero ECMWF/Open-Meteo baseline alongside +1 through +5 days. Because the pipeline retains normalized aggregates rather than provider hourly primitives, the server applies each forecast aggregate's anomaly from that homogeneous baseline to the latest server-verified AROME/soil observation, reconciles physical bounds and dependent hydrothermal windows, and then runs `hydrothermal-v1` with unchanged static habitat evidence. Missing required baseline fields, an observation-to-baseline gap above 8 hours, or an incomplete corrected input withholds the projection. If a completed later observation cycle crosses that seam, the pipeline invalidates and rebuilds the same-day issue; it does not weaken the calibration guard or silently overwrite a completed issue. Forecast rows remain separate from observations, carry issue and valid times, and expire after 36 hours or as soon as a target has expired. Hot storage retains the newest completed issue plus a newer replacement only while it is being built. The timeline retains conditional fruiting conditions and whole-cell opportunity separately; its whole-cell series is anchored to the latest observation, and per-horizon confidence is bounded by current and provider confidence.
- Static GIS processing runs outside Edge Functions because authoritative raster products are too large for request-bound runtimes.
- ICGC 1:50,000 geological units are kept in compact side tables as display-only context, separate from soil properties and scoring snapshots. Exact cells retain mapped/class/unit coverage sampled across the 250 m area; larger display cells are area-weighted from those canonical children, and map scale is never reported as metre resolution.
- Read functions return only verified cells in bounded views. Exact sensitive ecological locations are not collected or exposed.
- Historical occurrences are presence-only evidence, not training labels or a score multiplier. A record can corroborate ecological plausibility, but missing records never reduce suitability or imply absence. FungaCAT is accessed through its GBIF dataset key so the same records cannot be ingested twice under two source names.
- Occurrence responses expose counts, year ranges, provenance, DOI, and licence only at a minimum 10 km grid. The raw GBIF coordinates exist only in the authenticated ingestion request and the database mapping function; neither the source coordinates nor public point features are stored.
- Species-page habitat maps encode static land-cover/altitude/pH compatibility only. The GIS worker preserves every recognized land-cover fraction sampled within each 250 m cell, so a 35% compatible cover contributes 0.35 rather than turning the whole cell on. Effective habitat is `H = C × A`, where normalized `C` is exact compatible coverage after the static gates and normalized `A` is the shared altitude response inside that coverage; blue intensity represents this same `H`. A separate purple hatch marks compatible cells whose centres fall inside a 10 km occurrence-support cell, so historical corroboration cannot be mistaken for stronger habitat. Occurrence counts do not alter habitat compatibility; records outside compatible habitat remain a documented disagreement and unsampled cells are never excluded.
- Habitat reads use a compact generated forest field plus generated numeric altitude/pH fields on the canonical 250 m cells. `static_values` remains the verified source of truth. A measured covering index is retained because it keeps country-wide habitat aggregation index-only; live profiling showed that removing it caused a cold read to scan most of the table heap. The database reader plans exact 250 m viewport reads separately from coarse coverage aggregation, and coarse viewports use numeric bounds on the already-filtered resolution rather than materializing wide PostGIS rows.
- `hydrothermal-v1` reports one derived habitat fraction and two ordinal indices with one composite `modelVersion`: effective compatible area `H = C × A` on 0–1; conditional fruiting conditions `F = 100 × P × W^α × T^(1-α) × E` inside compatible habitat; and whole-cell opportunity `O = H × F`. `F` and `O` are 0–100 ordinal indices, while `H` is not a score; none is a probability of presence. `P` cosine-interpolates twelve month-centre phenology anchors derived from the one species calendar (`inactive=0`, `possible=.25`, `moderate=.5`, `good=.8`, `peak=1`), so display and scorer cannot drift. `T = 2^-((Tmean - Topt) / halfWidthSide)^2` gives a nonlinear response; the midpoint of each species' versioned numeric temperature range initializes `Topt`, and its endpoints initialize the half-response widths, unless an explicit species-literature override replaces them. `E` multiplies exponential frost- and heat-hour survival terms rather than applying a later cap. Unified water state `W = M × ((1-ρ) + ρQ) × V^βV × D^βD` combines shallow relative-extractable-water readiness `M`, effective-rain amount and wet-day frequency `Q`, vapour-pressure-deficit drying `V`, and dry-spell persistence `D`; rain, soil moisture, humidity, and drought never reappear as independent additive scores. `α` comes from a guild prior with an explicit species override. Every required component must be present: missing inputs withhold the result instead of renormalizing known components. Zero is biologically meaningful and propagates through the product. Map colour corresponds directly to the score band of `O`; compatible coverage is already present through `H` and is not applied again through colour opacity. All response constants are versioned low-confidence expert priors, not fitted estimates.
- A profile can opt into `predictionMode: "habitat_only"` when the short-term above-ground fruiting model is scientifically inapplicable. The scorer and prediction API then withhold `F` and `O`, the public map offers `H` compatibility only, and the profile must carry an explicit caveat. `Tuber melanosporum` uses this mode because its subterranean ascocarps develop over months and depend on host colonization, soil structure, management, and conditions at depth that the current inputs do not observe.
- A species page never scores a region centroid. Regional `O` quantiles and the median use equal-area 10 km display cells with verified non-zero compatible habitat; `H` is already inside each cell's `O` and is not applied as a second weight. The distinct regional `F` summary is weighted by effective compatible habitat because it answers a different question: conditions within the region's habitat. The interface exposes both semantics, the interquartile ranges, and cell counts. Neither summary is a whole-region presence probability or evidence that conditions are spatially uniform.
- The version-controlled habitat altitude range is the ecological core. Altitude remains at 100 through the interior, tapers linearly from 100 to 75 during the 100 m inside either documented limit, and then falls linearly to zero across the 100 m uncertainty margin outside each limit. For ranges narrower than 200 m, the two inner tapers meet at the midpoint. The potential-habitat reader receives the core limits, applies the shared taper and outer envelope to each exact 250 m cell, and aggregates both raw compatible coverage and altitude-weighted map intensity; cells at or beyond the zero-score edge remain excluded.
- Viewport coordinates are expanded to resolution-aware cache buckets before requests are made. Static habitat responses receive a one-day shared-cache lifetime and a model-version cache key; regional environmental snapshots and current prediction inputs keep a five-minute server/shared-cache lifetime. Browser map requests have a bounded deadline and discard obsolete responses after pans or species changes, so a stalled provider cannot leave the overlay loading indefinitely. Interactive 1/2.5/5/10 km reads use the compact species cache, while only close 250 m views evaluate canonical evidence on demand. Browser-facing map responses omit repeated provenance that is not used for drawing and negotiate gzip for material JSON bodies. Species profiles defer MapLibre and the static habitat request until the map is near the viewport, with a height-preserving accessible placeholder. A profile is not readable until every geographic cache batch is marked complete, so an interrupted rebuild cannot turn missing work into false zeroes. An optional versioned object-storage origin can serve static habitat JSON, with automatic database fallback. This keeps object storage off the critical path unless it is explicitly configured and populated.
- The hosted database is operated to a sub-450 MB target after physical compaction. The redundant 500 m materialization is omitted; the 1 km layer remains active until the original close-zoom transition to exact indexed 250 m cells. Four complete observed grid dates and the newest completed forecast issue are retained in PostgreSQL; longer hindcast validation should use an external export after measuring storage. Retention and vacuum run before the next UTC ingestion cycle so the oldest date's heap pages are reusable. Self-hosted Supabase/PostgreSQL in Docker is the capacity fallback if compaction plus retention cannot keep the database comfortably below the 500 MB Free limit.

Operational details, rebuild commands, and pipeline schedules are documented in [`supabase/README.md`](../supabase/README.md).
